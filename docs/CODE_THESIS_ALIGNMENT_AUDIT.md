This document records the mandatory pre-implementation audit. Classification meanings:

- **A** — The thesis requirement is valid and the code must be improved.
- **B** — The executable design is more correct and the thesis/presentation must later be corrected.
- **C** — Both descriptions are incomplete; a safer business design is required.
- **D** — The claim cannot currently be verified.

The governing priority is business correctness, tenant isolation, data integrity, executable code, tests, thesis, then presentation.

| AUD-05 | The candidate pool contains active staff assigned to the ticket organisation and is narrowed by project membership. | `backend/app/services/auto_assign.py`: `_compute_scores` filters active staff via `StaffOrgAssignment`; explicit project staff/manager membership narrows the pool only when such members exist. | Correct baseline; an empty project member list must not empty the organisation pool. | A | Preserve the fallback, share eligibility logic with manual assignment and AI reevaluation, and test organisation/project boundaries. |

| AUD-08 | Equal scores use least-recently-assigned round-robin. | `backend/app/services/auto_assign.py`: `find_best_assignee` prefers the oldest `last_assigned_at`, including never-assigned users, but lacks a final stable ID ordering. | Valid, but deterministic final ordering is required for reproducibility. | A | Sort by total score, never-assigned priority, oldest assignment time, then stable user ID. |
| AUD-09 | An organisation Redis lock prevents assignment races. | `backend/app/services/auto_assign.py`: lock key is organisation-scoped, but value is constant, release is unconditional, and a retry may proceed without owning the lock. Redis errors can propagate into ticket creation. | Lock ownership must be token-based; no process may delete another process's lock. Ticket creation must degrade safely. | C | Implement bounded token-owned acquisition/release and clear fail-safe behavior; test concurrent and Redis-failure paths. |
| AUD-10 | Ticket creation commits core data first and runs AI classification asynchronously. | `backend/app/api/tickets.py`: `create_ticket` flushes, computes SLA, assigns, commits, then enqueues `classify_ticket_task`; the request does not call Groq. | This is correct and protects ticket creation from provider failure. | A | Preserve the asynchronous boundary and add a test proving ticket creation succeeds when Groq is unavailable. |
| AUD-11 | The AI category is used immediately by the assignment algorithm during ticket creation. | `backend/app/api/tickets.py`: assignment occurs before the classification task is enqueued. `backend/app/services/auto_assign.py`: skill falls back to `ticket_type` when no prediction exists. `backend/app/tasks/ai_tasks.py`: stores predictions but does not reevaluate ownership. | The thesis wording is temporally impossible without blocking ticket creation. ## Initial implementation boundary

The first implementation tranche is limited to tenant-safe assignment eligibility, heartbeat presence, combined workload, deterministic scoring/locking, asynchronous two-stage AI handling, hybrid SLA reminders, directly related frontend behavior, tests, configuration, observability, and required documentation. Broader billing or deployment changes will only be made when they can be verified without destabilising the pre-defence system.

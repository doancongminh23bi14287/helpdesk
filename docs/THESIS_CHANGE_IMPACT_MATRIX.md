## Change-control note

The compatibility gate was introduced after commit `94a62a3` had already been implemented and pushed. The rows below therefore provide a retrospective impact review of that commit and establish the approval boundary for any follow-up work. No further source-code, schema, lifecycle, billing, or presentation change is authorised by this audit.

Classifications used in this matrix:

- **SAFE** — implementation correction that preserves the thesis architecture and claims.
- **THESIS-ALIGNING** — implements a valid feature already claimed by the thesis.
- **THESIS-CHANGING** — improves the solution but requires thesis or presentation wording, figures, metrics, or counts to change.
- **HIGH-RISK** — affects tenant isolation, data integrity, concurrency, lifecycle behaviour, production compatibility, or defence claims.

For a change that is both thesis-changing and security/lifecycle-sensitive, **HIGH-RISK** takes precedence. Such a row still lists every required thesis and slide correction.

## Migration gate

No migration is proposed by this audit. If a future change requires persistence that cannot safely use Redis, an existing audit/activity table, or a derived query, implementation must pause and add a new matrix row containing:

- old and new table counts;
- old and new Alembic revision counts and intended head;
- affected ERD entities/relationships;
- exact Chapter III/IV sections, tables and figures;
- upgrade, downgrade, lock and production-data risks.

Historical migration files must not be edited.

## Proposed implementation plan — approval boundary

1. **Freeze source behaviour at `94a62a3`** while GitHub Actions evaluates the pushed commit.
2. **Review CI evidence** and record collected/passed/failed/skipped/duration without changing tests to hide failures.
3. **Resolve only SAFE or clearly THESIS-ALIGNING defects** that CI proves, with a new matrix row before each code change.
4. **Do not modify TC-01, TC-02, TC-05, TC-06 or TC-07** without explicit approval because they are HIGH-RISK.
5. **Do not revise the 40/40/20 weights, ticket lifecycle or billing rules.** Any proposal to do so requires measured business evidence and a new HIGH-RISK row.
6. **Do not edit the thesis PDF or PowerPoint under the current repository task.** Use the listed corrections as a controlled hand-off for later document work.
7. **Do not publish load/performance capacity claims** until an authorised run records environment, dataset, duration, user mix, P95, P99, throughput and error rate.

Audit-phase stop: this document and the plan are the only changes made under the new gate. All HIGH-RISK and THESIS-CHANGING follow-up implementation remains paused pending review.
